# ADR-0001: 采用按运行边界划分的单仓库目录

- 状态：已接受
- 日期：2026-10-14
- 关联：MVP F1–F17、D1–D11

## 背景

MVP 同时包含本地采集器、服务端、Web 页面、事件契约、数据库和演示素材。这些部分需要共享产品约束和证据模型，但具有不同的运行、安全和发布边界。当前尚未锁定具体框架版本与完整构建工具链。

## 决策

使用一个 Git 仓库，并按运行边界建立顶层目录：`collector`、`server`、`web`、`contracts`、`database`、`demo` 和 `scripts`。各模块通过明确的事件/API 契约协作，不跨模块直接引用内部实现。

本次只建立目录职责和占位文件，不创建不可运行的伪应用，也不借此锁定 Java、Spring Boot、Node、包管理器或数据库迁移工具的具体版本。版本和构建入口在首次实现对应模块时另行记录。

## 备选方案

- 按领域能力拆成更多模块：边界更细，但 MVP 阶段增加构建与维护成本。
- 立即拆成多个仓库：发布隔离更强，但契约联调、文档同步和初期变更成本更高。
- 所有代码放在单一应用目录：启动简单，但会混淆采集端与服务端的权限、安全和部署边界。

## 后果

- 团队能在同一变更中同步更新事件契约、服务端和采集器，同时评审各自的安全边界。
- 目录本身不代表模块已经可构建或运行；README 和构建配置必须如实反映实现状态。
- 未来如需独立发布模块，可以沿现有顶层边界拆分，而无需先重组业务代码。

## 验证与回退

首个端到端切片完成后，检查跨目录依赖是否只经过 `contracts` 中的公开契约。如果布局导致循环依赖或无法独立发布，再用新的 ADR 调整目录并记录迁移方法。
