# 工程规范

本规范将公开工程实践转化为 BugTrace 的轻量约定。原则是保持代码一致、变更容易审查、关键结论可验证。参考了 [Google 工程代码评审指南](https://google.github.io/eng-practices/)、[Google Java 风格指南](https://google.github.io/styleguide/javaguide.html)、[Microsoft Engineering Fundamentals Playbook](https://microsoft.github.io/code-with-engineering-playbook/) 和 [Airbnb JavaScript 风格指南](https://github.com/airbnb/javascript)。这些资料是参考，不意味着照搬其全部规则；项目中的格式化器、静态检查配置和本文件一旦建立，应成为唯一可执行标准。

## 通用原则

- 清晰胜过炫技；优先最小且完整的改动，避免隐藏状态和不必要的通用框架。
- 一个函数/模块围绕一个明确职责组织。规则判定保持确定性，模型调用、IO 和 UI 状态放在边界层。
- 输入、持久化数据、Git 输出、模型响应和外部 API 响应都视为不可信数据，先校验再使用。
- 错误应保留可诊断上下文，但不能泄露秘密；失败、超时和降级必须能被调用方识别。
- 不增加未批准的 MVP 功能。新依赖应说明用途、维护状态、许可证及其带来的安全/部署影响。
- 对外接口和持久化格式优先显式版本化；改变行为时记录兼容影响。

## 命名与格式

- 使用仓库配置的格式化器和静态检查器；禁止仅依靠 IDE 默认设置形成隐式风格。
- Java 使用标准 Java 命名：类型用 `UpperCamelCase`，方法/字段用 `lowerCamelCase`，常量用 `UPPER_SNAKE_CASE`；包名小写。
- Vue/JavaScript/TypeScript 的具体分号、引号、导入排序与组件命名，待前端脚手架建立后通过 ESLint/Prettier 配置确定；不要在本规范与工具配置中维护两套规则。
- 文件、API、事件类型和数据库字段命名应稳定、可搜索，并在同一概念上使用同一个词。
- 注释解释理由、约束或非显然行为，不复述代码。公共边界、复杂规则和安全敏感逻辑需要说明不变量。

## Java 与服务端

- 以项目实际选定的 Java 版本为准（MVP 方案目前写为 Java 17/21，尚未选定）。在版本锁定前不要使用某个版本特有 API。
- Spring MVC/API 层负责协议和参数校验；业务规则放在独立服务/领域逻辑中；数据库访问集中在持久化层。避免控制器中直接编排复杂规则或模型提示词。
- MyBatis-Plus 查询必须显式限定项目/会话等租户边界；分页和排序参数应验证；禁止把用户输入拼接为 SQL 片段。
- 时间统一以 UTC 存储、以带时区格式传输；ID、金额等数据不得用易丢精度的浮点数表达。
- 配置通过类型化配置项注入；敏感配置只能通过环境或密钥管理提供，不写入仓库默认值。
- 异步任务需要定义超时、重试上限、幂等键和最终失败状态；不得无界重试或无限制并发调用模型。

## 前端

- Vue 组件保持单一职责；页面编排与可复用展示组件分开，服务端状态通过明确的 API 层访问。
- 页面必须区分加载、空数据、错误、权限不足和降级状态；不要将 Agent 草稿显示成已确认方案。
- 显示 Agent 内容时保留来源、证据和“推断/未验证”状态；来源信息不能被样式或摘要隐藏。
- 用户触发的开始、结束、移出事件、确认入库等关键操作应有清楚的结果反馈和必要的二次确认。
- 处理模型生成文本时按不可信内容渲染，避免直接注入 HTML。

## API、事件与数据

- API 使用一致的资源和错误格式；请求校验错误应指出字段，业务冲突使用稳定错误码。
- 采集事件包含唯一事件 ID、项目/会话关联信息、发生时间、事件类型和 schema 版本；重复上传必须幂等。
- 对日志、diff 和模型输出设置大小上限，并明确截断标记。不得把“截断后的内容”呈现为完整证据。
- 证据引用必须指向系统中存在的事件、提交、文件及 diff 片段；验证失败时不能静默接受。
- 数据库 schema 变更应包含迁移脚本及升级/回滚说明；破坏性迁移需先定义数据兼容方案。

## 测试与可观测性

- 新增或修改的规则逻辑应设计可重复的边界场景；涉及脱敏、幂等、证据校验、钩子禁用和路径限制的改动应覆盖对应风险。
- 测试不得依赖真实模型、真实用户仓库或不稳定网络；通过固定输入/响应验证编排与校验行为。
- 日志记录事件 ID、会话 ID、任务状态、耗时和降级原因等诊断字段；禁止记录凭据、原始敏感输出或完整模型提示词。
- 指标至少能区分采集丢失/重试、规则判定、模型校验失败/降级和用户确认结果。日志与指标都不能成为绕过脱敏的旁路。

## 代码评审

- 变更应聚焦且便于理解；较大工作拆成逻辑独立的小变更。PR 描述写清目标、实现、风险和验证结果。
- 评审优先检查正确性、边界条件、安全与隐私、可维护性和测试，而非个人偏好。
- 阻断性问题说明具体影响并给出可操作建议；纯风格偏好应遵循已配置工具，不以主观意见阻塞。
- 在 CI、格式化和静态检查尚未搭建前，PR 必须诚实说明未执行的检查，不得以“通过”代替未运行。
